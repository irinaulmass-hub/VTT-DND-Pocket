# Роли и границы доступа D1

Аудит кода на `dc85cd5`. Ниже описаны существующие проверки и целевой контракт для C1/D2. Персональная авторизация пока не реализована.

| Роль | Целевой доступ |
| --- | --- |
| Мастер | Полная кампания, редактор, назначения персонажей и публикация открытий |
| Игрок | Карточка и проекция карты назначенного героя, действия в пределах выданных мастером полномочий |
| Телевизор | Опубликованная общая проекция, только чтение и повторная синхронизация |
| Гость | Подключение и получение назначения, без карточек и закрытых данных кампании |

## Подтверждённые ограничения текущего кода

- `player-login` выбирает героя по имени, а `claim-character` принимает ID и имя от клиента. Выбор кампании через `game` проверяет её существование. Эти механизмы ещё не подтверждают право на героя или кампанию.
- `GET /api/characters`, `GET /api/players` и `request-characters` возвращают полные карточки. Изменения карточек рассылаются обычным клиентам через `CHARACTERS_UPDATE` и `PLAYER_DATA_UPDATE`.
- `GET /api/scenes` выдаёт список сцен, а `/api/maps`, `/api/tiles`, `/api/audio` и `/assets` открывают каталог и ресурсы. В доступном изображении могут находиться закрытые участки. Для персональной карты понадобится проверять выдачу ресурса вместе с проекцией.
- `GET /api/worlds/table` фильтрует тайлы по общей маске и скрывает объекты с `hidden`, но возвращает все жетоны. `WORLD_UPDATE` содержит среднюю позицию партии. Эти данные требуют отдельных проекций для разных героев.
- `POST /api/loot/:id/take` проверяет открытость контейнера, ревизию и наличие персонажа в кампании, но позволяет указать чужой `characterId`. `interact-object` проверяет видимость объекта, но не личность игрока. `interact-lightbox-object` принимает объект состояния и рассылает его без проверки определения объекта.
- `view=table` ограничивает WS-команды и типы событий, но параметр выбирает клиент. Эта роль не защищает HTTP-запросы из того же браузера. Cookie мастера распознаётся HTTP независимо от открытого экрана.
- `sendFullState` использует `sendView`, который фильтрует некоторые объекты и события. Прямые вызовы `ws.send` обходят эту функцию. Каждый такой ответ должен получить явный контракт роли.
- Уже защищены редактор, черновики мира и карт, заметки, библиотека, каталог, приключения и ссылки локаций. Фильтры скрытых объектов и секретных особенностей проверяются существующим интеграционным тестом.

## Порядок реализации

C1 вводит назначение героя мастером и серверное полномочие, привязанное к кампании и ID героя. Имя остаётся отображаемым полем. Смена героя и отзыв назначения прекращают старый доступ, включая уже открытый WS. Телевизор получает отдельное полномочие чтения, чтобы открытие его экрана в браузере мастера не давало клиентскому коду мастерский API.

D2 применяет одну модель полномочий к HTTP, WS, первоначальному снимку, рассылке, повторной синхронизации и ресурсам. Сначала закрываются полные карточки и выбор чужого героя, затем добыча и взаимодействия, затем списки сцен, изображения и персональные проекции мира. До подключения личного тумана проверяется отсутствие скрытых данных во всех этих каналах.

Приёмка C1/D2 должна включать два телефона, ТВ и гостя, подмену ID героя и кампании, отзыв доступа, повторное соединение, HTTP с cookie мастера на телевизоре, прямые WS-ответы и чтение ресурсов по известному URL. Существующие проверки общего экрана не являются приёмкой персональной приватности.

## Реализованный шаг C1a

Мастерские `GET/POST /api/player-access` и `DELETE /api/player-access/:characterId` управляют назначениями в текущей кампании. POST принимает `characterId` и однократно возвращает токен приглашения. В файле `player-access.json` хранится его хеш. Новое приглашение заменяет прежнее для этого героя. `GET /api/player-access/current` принимает `Authorization: Bearer <token>` и возвращает ID героя либо HTTP 401. Интерфейсы и WS подключаются в C1b. До этого прежний выбор героя и выдача карточек продолжают действовать.

## C1b

Мастер открывает /dm/access.html и передаёт игроку ссылку на /player с приглашением во фрагменте URL. Личная карточка сохраняет приглашение в локальном хранилище текущей кампании и передаёт его через player-auth. Повторная выдача и отзыв закрывают назначенные соединения. Старые player-login и claim-character отклоняются. Полное закрытие гостевых HTTP и WS-каналов, включая выдачу карточек до входа, относится к D2. Проверка интерфейса в браузере ещё требуется.

## D2a

GET /api/characters и GET /api/players возвращают мастеру весь список, игроку с Bearer-приглашением только назначенного героя, гостю пустой список. WS-ответы и рассылки карточек используют ту же привязку к ID. Передача добычи в чужую карточку отклоняется с HTTP 403. Взаимодействие гостя с объектами отклоняется. Карты и ресурсы общего экрана и отдельная фильтрация мастерских полей остаются в D2b.

## D2b1

Модуль character-view.js задаёт разрешённые поля карточки для игрока. Он применяется к HTTP /api/characters и /api/players, входу player-auth и всем сообщениям CHARACTERS_UPDATE и PLAYER_DATA_UPDATE. Предметы и умения имеют отдельный список полей. Скрытые записи исключаются. Характеристики, навыки и ячейки заклинаний фильтруются по известным ключам. Денежная сумма поддерживается как скаляр или разбивка по cp, sp, ep, gp и pp. Мастер получает исходные данные. Ограничение карт и ресурсов остаётся в D2b2.


## D2b2

Каталоги сцен, карт, тайлов и музыки и служебное состояние доступны мастеру. Исходные файлы из /assets/maps и /assets/audio требуют сессию мастера. Маршрут /presentation/assets отдаёт выбранное изображение сцены, текущую музыку и связанные карты открытых эффектов. Разрешение проверяется по текущей кампании при каждом запросе. Эти ответы помечены no-store. Исходники редактора с расширением .map.json закрыты, отдельный маршрут головоломки по-прежнему проверяет открытие связанной карты.

Общий экран доступен по /tv и использует опубликованную проекцию только для чтения. Запросы API из /tv отправляются без cookie и с view=table. Сервер учитывает этот режим и при переданном cookie мастера. WebSocket телевизора разрешает только request-sync. Обычные вкладки одного браузера разделяют cookie, поэтому отдельный профиль нужен, если устройство должно использоваться без мастерской сессии на уровне браузера.

После публикации растровая карта передаётся целым изображением. Туман поверх неё управляет показом в интерфейсе. Личная серверная выдача по открытым тайлам относится к этапу E.


## Личные позиции C2

GET и PUT /api/character-positions/:characterId требуют сессию мастера. GET /api/player-position использует действующее приглашение и определяет героя на сервере. Гость и приглашение другой кампании получают HTTP 401. Общий экран получает отдельные опубликованные жетоны через действующий маршрут карты.


## Движение C3

POST /api/player-position/move требует действующее приглашение. Герой определяется на сервере. Поля для подмены героя, мира или координат в запросе отклоняются. Событие CHARACTER_POSITION получают назначенный игрок и мастер текущей кампании. Телевизор сохраняет общий снимок.


## Переходы C4

Мастерские маршруты /api/worlds/:id/transitions доступны с мастерской сессией и проверяют текущую кампанию. Команда enter через /api/player-position/move использует текущую позицию назначенного героя. Клиент не задаёт карту назначения. Сообщение о переходе использует приватное событие CHARACTER_POSITION, а телевизор показывает открытую местность опубликованной сцены.


## Двери E2

Состояние двери меняет мастер через PUT /api/worlds/live/doors/:doorId. Маршрут проверяет активную карту и принадлежность двери опубликованной версии. Обновление телевизора использует общую маску текущего этажа. Скрытые двери фильтруются при выдаче карты.


## Раскрытие секретов E4

Команда раскрытия требует сессию мастера и актуальную публикацию в выбранной кампании. Приглашение героя и режим `view=table` не дают право выполнить команду. Полный список скрытых объектов доступен мастеру. До явного раскрытия скрытые объекты исключаются из `GET /api/worlds/table` даже на исследованной клетке и при выключенном тумане.

После раскрытия общедоступный снимок активной карты выдаёт разрешённый объект в запрошенном чанке. Событие `WORLD_UPDATE` предлагает обновить снимок карты и не содержит сведений о секрете. Личные передачи описаны в D4.


## Личные открытия D4

`PUT /api/worlds/live/secrets/:objectId/share` требует сессию мастера и принимает `id`, `revision` опубликованного черновика и `characterId` героя текущей кампании. Команда привязана к скрытому объекту актуальной активной карты. Общая проекция и её версия при личной передаче сохраняются.

`GET /api/player-discoveries` определяет получателя по действующему Bearer-приглашению в текущей кампании. Ответ с `Cache-Control: no-store` содержит снимки только этого героя. Гость, запрос в режиме ТВ и запрос с одной мастерской cookie получают HTTP 401. Подмена ID через параметры запроса не меняет получателя.

Уведомление `PLAYER_DISCOVERIES_CHANGED` отправляется только сокетам получателя в этой кампании и содержит ID героя. Карточка открывает сокет в режиме `view=player` и подтверждает назначение приглашением, в том числе в браузере с мастерской сессией. Карточка перечитывает журнал после входа, уведомления и открытия вкладки «Путь». Отозванное приглашение теряет доступ к журналу. Новое приглашение того же героя получает его прежние открытия.

Игрок использует прежнюю команду `enter` с ревизией собственной позиции; адрес назначения задаётся только серверной парой. Для новых пар нельзя перейти в неопубликованный интерьер. Снимки привязки не передаются в публичном HTTP/WS. Старые односторонние переходы C4 сохраняют свой контракт.

## История District F5d3

Прежние мастерские POST district-preview и PUT карты обслуживают подписанную историю. Подписи before/after выдаются только мастеру вместе с полным предпросмотром. Вариант districtGuard с historyProof проходит requireDm, ревизию карты, хеш списка переходов, HMAC снимка и контекста карты/кампании, текущие пары и входные клетки. Он не разрешает произвольный импорт под видом Undo и не передаётся на ТВ/телефоны. Ключ процесса не записывается в кампанию; после рестарта старая подпись отклоняется.
