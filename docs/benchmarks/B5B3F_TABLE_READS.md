# B5b3f — чтение общего экрана с насыщенной памятью

14 ноября 2026. База приложения — `abc25599dcc006c91da9933d9de6e3481ce3860b`. Это диагностика, не оптимизация рабочего сервера. Производственные модули, формат хранения, графика, лимиты и зависимости не менялись. applicationRef в выборках null: точные SHA-256 всех измеряемых исходников сохранены в sourceSha256 и совпадают во всех пяти финальных прогонах.

## Стенд и исходные данные

Новый scripts/world-table-benchmark.cjs переиспользует генератор из существующего world-benchmark. Временный DATA_DIR создаётся независимо от внешнего DATA_DIR, сервер запускается отдельным процессом с прежним guarded preload. Родитель хранит эталон вне измеряемого сервера; запросы идут последовательно через настоящий публичный GET /api/worlds/table без cookie мастера.

Две дополнительные клетки памяти включают историческое/пустое наблюдение вне исходного terrain; лимит тайлов самой карты не повышался. Семь объектов заменены контрольными, общее число сохранено. Один герой наблюдает новое местоположение перемещённой таверны. Есть старый снимок двери, память прежней местности, пустая запомненная клетка, объект без известной опоры, секрет с разрешением и без, кронa из отрицательного соседнего чанка и объект только в памяти. Пользовательские кампании не использовались.

Пять запросов: near — 0,0; adjacent — четыре чанка у начала координат, включая отрицательный; distant — четыре заполненных удалённых чанка; live — новая позиция наблюдаемого объекта; empty — удалённый пустой чанк. Полные ключи есть в method.queries. Один прогрев каждого запроса исключён, затем пять выборок. Кеш ОС прогрет, GC не принудительный. Linux x64, Node.js 24.22.1, AMD EPYC 9V74; прогоны выполнялись последовательно после тестов. Физические устройства, браузер/FPS, LAN/Wi-Fi и Windows не измерены.

## Результаты

Медианы двух повторов с туманом. Время HTTP включает получение и JSON.parse в клиенте стенда; проверки ответа выполняются после замера.

| Запрос | HTTP A / B, мс | Сервер A / B, мс | Прочитано байтов | Ответ, байтов |
| --- | ---: | ---: | ---: | ---: |
| near | 31.61 / 39.78 | 30.75 / 38.86 | 4,417,091 | 4,994 |
| adjacent | 23.06 / 26.96 | 22.18 / 25.77 | 4,419,152 | 9,362 |
| distant | 26.65 / 24.28 | 24.91 / 22.24 | 4,471,320 | 101,471 |
| live | 22.96 / 22.79 | 21.36 / 21.72 | 4,414,875 | 386 |
| empty | 23.19 / 23.71 | 22.07 / 22.52 | 4,414,875 | 232 |

Для empty не читается ни одного файла terrain, но каждый запрос всё равно читает **392 532 байта опубликованного манифеста** и **4 022 228 байт character-positions.json**. Последний содержит маски, память и позиции всего файла кампании. Это основная доля 4 414 875 байт входного чтения при ответе всего 232 байта.

Эксклюзивные selfMs для empty (основные стадии):

| Стадия | A, мс | B, мс |
| --- | ---: | ---: |
| store.readPublished | 1.58 | 1.57 |
| io.publishedManifest | 0.26 | 0.27 |
| io.positions | 1.95 | 1.90 |
| positions.mapState | 14.93 | 15.03 |
| movement.visibleCells | 0.23 | 0.28 |
| exploration.project | 2.06 | 2.23 |
| response.json | 0.31 | 0.29 |

store.readPublished self включает разбор JSON манифеста и выбранных чанков и сборку объекта, за вычетом вложенного файлового чтения. positions.mapState self включает разбор всего JSON состояния, подсчёт размера прочитанных строк диагностикой и подготовку состояния, за вычетом I/O и visibleCells. Это не отдельный чистый замер JSON.parse. response.json включает сериализацию Express, заголовки и отправку, а не только JSON.stringify. io.* и readCategories.readMs измеряют синхронное чтение/декодирование с возможными паузами GC; подсчёт байтов исключён из readMs. Время вне обёрток дано как unmeasuredMs. Inclusive totalMs суммировать нельзя, медианы независимых стадий также не обязаны складываться.

Стоимость запроса заметно колеблется: near HTTP 31.61 / 39.78 мс при контрольном запуске без стадий 24.06 мс. Обёртки и измерения добавляют издержки, GC/аллокатор/ОС не фиксированы. Поэтому эти числа не являются обещанием задержек рабочего приложения или доказательством ускорения. У empty контрольная HTTP-медиана 21.19 мс; при 600 объектах с туманом — 8.21 мс. Даже без тумана в большом профиле mapState читает и разбирает тот же файл памяти: empty HTTP 21.85 мс. Фильтрация объектов становится дешевле, но основное чтение остаётся.

## Проверки корректности

Полный npm test — **99/99**, без пропусков. Два новых теста: настоящий HTTP с насыщенной памятью, согласованность эксклюзивных стадий и байтов/категорий, отсутствие записей, сохранение внешнего DATA_DIR и старого отчёта, равенство ответов с обёртками и без, действующая разница тумана; неверные параметры отвергаются до запуска сервера. Существующие проверки HMAC, District, ролей, памяти/границ и коллизий проходят. Проверен синтаксис пяти изменённых/новых JS.

Каждая выборка сравнивает весь HTTP-объект с полной моделью опубликованного снимка и состояния, а также независимые ожидания: private-поле и нераскрытый сундук отсутствуют; совпадающее разрешение раскрывает второй сундук; неизвестная опора не раскрывается под туманом; старая дверь остаётся открытой в памяти; новая видимая таверна подавляет старый снимок вне запроса; отрицательный выступ кроны не теряется; ID не дублируются. Существующие отдельные модульные/HTTP-тесты закрепляют сам алгоритм project, эталон стенда не заменяет их.

LIMIT_FOG_A, LIMIT_FOG_B и LIMIT_CONTROL имеют одинаковые responseSha256 для всех пяти регионов, одинаковые исходники и размеры состояния. Все измеренные записи равны нулю. Источники финальных файлов повторно сверены с sourceSha256. Контроль off отключает стадии, но сохраняет измеритель HTTP/I/O: это тоже диагностический процесс.

## Следующий срез B5b3g

Выбрано **ограниченное повторное использование разобранного состояния для read-only mapState** до введения дискового пространственного индекса. Причина — стоимость полного файла исследования существенно больше манифеста и пространственной фильтрации. Индекс объектов отдельно не уберёт эти 4 МБ на каждый запрос. Этот срез ещё не реализован.

Контракт: один кешированный документ на фабрику, привязанный к полному пути кампании и идентичности файла (device/inode, size, mtimeNs/ctimeNs); принимать документ только при неизменной идентичности до/после чтения. Допускать кеш только для файла до 8 MiB, при превышении — прежний полный путь. Это предел размера входного документа, не обещание 8 MiB JS heap. Вытеснять прежнюю кампанию/версию и явно инвалидировать собственные записи. Ошибка/удаление/подмена файла не должны возвращать прежние данные. Изменяющие операции продолжают читать свежий независимый объект; кеш не хранит вычисленный visible, проекцию, роли или раскрытые объекты. Нельзя вернуть изменяемое общее состояние мутатору.

Критерии: одинаковые публичные ответы с полным чтением; после первого чтения неизменённый файл не читается/не разбирается повторно; запись позиции/двери/тумана/секрета, смена кампании, рестарт и внешняя атомарная замена немедленно видны; ошибка/oversize не ломают прежний путь. Повторить этот стенд с контролем и теми же контрольными объектами, проверяя байты, время и память. HMAC, legacy, формат хранения и лимиты карт не менять. B5b3 целиком остаётся открытой: холодное полное чтение и линейный обход метаданных ещё потребуют отдельного пространственного решения.

## Воспроизведение

```bash
npm test
npm run benchmark:table -- --profile medium --samples 5 --fog on --stages on --output /tmp/table-medium-new.json
npm run benchmark:table -- --profile limit --samples 5 --fog on --stages on --output /tmp/table-limit-a-new.json
npm run benchmark:table -- --profile limit --samples 5 --fog on --stages on --output /tmp/table-limit-b-new.json
npm run benchmark:table -- --profile limit --samples 5 --fog on --stages off --output /tmp/table-control-new.json
npm run benchmark:table -- --profile limit --samples 5 --fog off --stages on --output /tmp/table-clear-new.json
```

Запускать последовательно, выбирать новые output: существующий файл не перезаписывается. Для каждого следующего сравнения сохранять sourceSha256, responseSha256, исходные rows и условия; не сопоставлять абсолютные времена с иным стендом как контроль оптимизации.
