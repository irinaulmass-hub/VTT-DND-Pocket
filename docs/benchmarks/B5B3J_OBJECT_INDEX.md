# B5b3j — производный индекс объектов общего экрана

14 ноября 2026. База — `4ff46f7ca1aacff6345761373c532f7691b9a14d`. Индекс ускоряет повторную проекцию неизменяемых опубликованных объектов и памяти. Формат хранения, HTTP/WS, HMAC, физика/LOS, права, лимиты карт и графика не менялись. Пользовательские кампании не использовались.

## Реализация

world-object-index.js строит производные корзины по чанкам visualBounds и отдельный Map ID → объект. Опора добавляется в корзины независимо от рисунка: это сохраняет прежнюю быструю проверку intersects, включая неизвестный legacy-kind. select объединяет порядковые номера без дублей и сортирует по исходному порядку; числовые ключи словаря памяти следуют прежнему Object.values. Само пересечение и авторизация дополнительно проверяются прежними условиями проектора.

Два отдельных кеша в world-exploration — один для текущей коллекции живых объектов, второй для памяти. Каждый удерживает только последнюю допущенную неизменяемую коллекцию; новый источник/отказ вытесняет запись, memory-кеш очищается без тумана. Индекс привязан к ссылке конкретного снимка, не к ID карты или ответу. Условия допуска: замороженная стандартная коллекция и записи с собственными неизменяемыми данными id/kind/x/y/turn; корректные координаты/повороты, уникальные ID. Accessor-поля и нестандартный iterator не допускаются. Лимит — 3 000 записей, 15 000 членств в корзинах и не более 16 визуальных чанков на объект. Это допуск индекса, не ограничение чтения пользовательских данных: при отказе используется полный прежний обход. Источники рабочего сервера уже ограничены допуском JSON-документов B5b3g/i; это не оценка JS heap.

Живой проход получает только геометрических кандидатов. Для памяти проверка текущей видимости ID остаётся глобальной: find извлекает актуальный живой объект даже вне запрошенных чанков и заново проверяет hidden/reveal и visible по опоре. Если живой индекс недоступен, прежний полный проход строит глобальный liveIds. Поэтому видимая новая позиция подавляет старую память, но нераскрытый скрытый объект не делает этого. Оба индекса работают независимо: возможны оба смешанных fallback-режима. Маски, приоритеты, снимок open двери и публичный whitelist прежние; решения доступа/видимость/готовые ответы не кешируются.

## Проверки

Полный npm test — **115/115**, без пропусков, Node.js 24.22.1. Синтаксис восьми новых/изменённых JS проверен. Пять сценариев test/world-object-index.test.cjs:

1. Отбор опоры/выступов, отрицательные координаты, повороты, неизвестный kind, непереставляемый порядок, числовые ключи памяти, пустые/неканонические запросы и вытеснение/очистка.
2. **448 сравнений** с независимым линейным алгоритмом: 16 наборов по 160 объектов × четыре сочетания замороженных/изменяемых источников × семь запросов. Проверяются структурное и JSON-побайтовое равенство с масками/секретами/памятью и отсутствие private-полей.
3. Глобальное подавление перемещённого объекта вне запроса, matching reveal, состояние двери в памяти, false-приоритет масок и блокировка свежего fallback запомненной местностью.
4. 3 000 наблюдаемых через Proxy объектов: после прогрева локальный запрос читает меньше 30 полей x, пустой — ноль; линейный эталон читает тысячи. Новый снимок и изменение авторизации видны без старого индекса.
5. Отказ для изменяемых записей, повторных ID, accessor-полей/корня, нестандартного iterator, превышения числа записей, размеров и общей ёмкости корзин; полный fallback остаётся эквивалентным и свежим.

test/fixtures/world-exploration-linear.cjs содержит независимую копию алгоритма из 4ff46f7 с исправленным только путём require и поясняющим комментарием. Она сверена с исходным Git blob; не подключается в рабочем сервере. HTTP-стенд подтверждает отсутствие перестроений/отказов после прогрева допустимых снимков и ноль кандидатов в геометрически пустых регионах. Прежние реальные HTTP/VM сценарии ролей/кампаний/тумана/памяти/публикации/перезапуска и D3 проходят. Новая браузерная приёмка не проводилась.

## Методика измерений

[Контроль с туманом](B5B3J_CONTROL_FOG.json), [без тумана](B5B3J_CONTROL_CLEAR.json): отдельная копия проекта с точным world-exploration.js базы 4ff46f7. Новый файл индекса присутствует для одинакового sourceSha256, но линейный проектор его не загружает. Остальные диагностические файлы совпадают. [Индекс A](B5B3J_INDEXED_FOG_A.json), [повтор B](B5B3J_INDEXED_FOG_B.json), [без тумана](B5B3J_INDEXED_CLEAR.json) — текущая реализация после тестов.

Из измеряемых хешей отличается только world-exploration.js, который подключает новый индекс. Соответствующие responseSha256 совпадают для всех шести запросов и обеих настроек тумана, измеренных записей нет. applicationRef=null; точные sourceSha256 сохранены. Референс и модуль контроля сверены с базой.

125 районов/3 000 живых объектов/150 000 тайлов/599 чанков, память — 2 997 объектов и 150 002 исторические записи клеток. Публичный loopback HTTP без cookie мастера, отдельные процессы и временные DATA_DIR. Шесть последовательных запросов; первый цикл теперь сохранён отдельно в **warmupRows**, не входит в summary. Затем пять измеренных циклов: по 30 строк на прогон, всего 150 измеренных и 30 первых запросов.

Guarded preload измеряет index.get/select/find и счётчики кандидатов/поисков/построений/отказов. Счётчики не обходят коллекции сами. В контроле они отсутствуют, потому что индекс не вызывался; это не означает ноль линейной работы. В stage-off режиме хуки отсутствуют, но сам алгоритм индекса работает и возвращает тот же ответ. Никакая диагностика не подключается при обычном запуске.

Среда: Linux x64, Node.js 24.22.1, AMD EPYC 9V74; кеш ОС прогрет, GC не принудительный. wallMs включает получение и JSON.parse, утверждения после таймера. Стадии имеют overhead, inclusive totalMs не суммировать; независимые медианы не складываются. readBytes исключает stat/exists. Браузер/FPS/LAN/Wi-Fi/Windows/физические устройства не измерялись.

## Повторные запросы

HTTP-медианы с туманом, мс; кандидаты — сумма живого и запомненного отбора до авторизации.

| Запрос | Линейный | Индекс A / B | Кандидаты |
| --- | ---: | ---: | ---: |
| status | 0.85 | 0.74 / 0.82 | — |
| near | 3.87 | 1.32 / 1.36 | 18 |
| adjacent | 4.03 | 1.59 / 1.43 | 34 |
| distant | 6.52 | 3.56 / 3.57 | 0 |
| live | 3.49 | 1.09 / 1.12 | 1 |
| empty | 3.62 | 1.04 / 1.09 | 0 |

Линейный проектор с туманом каждый раз проходит 3 000 + 2 997 записей. Ближний запрос выбирает **18 кандидатов и 8 глобальных ID-поисков**, соседние чанки — 34/16, пустой и дальний регионы — 0/0. После прогрева построений и отказов нет. Empty HTTP **3.62 → 1.04 / 1.08 мс**, selfMs проекции **2.322 → 0.006 / 0.006 мс** (работа индекса выделена отдельно). Near HTTP **3.87 → 1.32 / 1.36 мс**. В дальней области остаётся проекция 4 096 запомненных клеток, поэтому она дороже пустой.

Без тумана near **1.62 → 1.24 мс**, empty **1.55 → 0.92 мс**, память не индексируется. Status не использует индекс и не объявляется ускоренным. Байты I/O и ответов не изменились: срез уменьшает вычисления отбора, а не объём транспорта/файлов.

## Стоимость первого построения и ограничения

Первый near после status (данные уже прочитаны, но проектор/индекс впервые используются): линейный **14.77 мс**, индекс **39.83 / 67.94 мс**. Из них index.get с двумя построениями занимает **32.21 / 59.77 мс**. Без тумана одно построение: near **14.01 → 27.20 мс**, index.get **22.68 мс**. Эти единичные строки включают JIT/аллокатор/возможный GC и не являются стабильной медианой холодного запроса, но показывают заметную первоначальную цену. Она не скрыта в summary и не объявляется улучшенной.

Новая ссылка снимка, смена кампании/карты или отказ допуска заставляют перестроить индекс либо перейти на полный путь. Сейчас даже изменение только кадра/жетонов переписывает манифест и создаёт новую коллекцию объектов, а изменение памяти при исследовании — новый словарь памяти. Частые такие изменения не измерялись как отдельная сессия и могут уменьшить выигрыш. Холодное полное чтение и дисковый пространственный индекс остаются открытыми. B5b3 целиком не завершена.

Пик RSS с туманом: контроль 102.64 MiB, индекс 105.03/102.74 MiB. Это конкретные прогоны без фиксированного GC; экономия памяти/верхняя граница heap не заявляются. Индексы дополнительно удерживают ограниченные коллекции и корзины.

## Следующий срез B5b3k

Сохранить стабильную неизменяемую коллекцию опубликованных объектов в readPublishedView при изменении только кадра/жетонов/seen/fog. Это позволит не строить живой индекс заново при неизменной геометрии. Переиспользовать ссылку только после проверки полного равенства содержимого и порядка объектов; hidden/публичные поля и порядок нельзя подменять старой записью. Новые геометрия, состав, порядок или поля объектов должны давать новый источник/индекс. Независимые мутирующие чтения, проверка идентичности файла, ошибки/oversize/legacy и ограничение числа документов прежние.

Критерии: тот же публичный ответ, ноль перестроений живого индекса после правки только состояния карты, свежий индекс после изменения объектов/секретных флагов и сохранность исходных снимков. Добавить в стенд управляемое изменение состояния между чтениями и записать цену первого/повторного запроса. Не менять формат/физику/LOS/лимиты и не заявлять устранение всех холодных перестроений памяти исследования.
