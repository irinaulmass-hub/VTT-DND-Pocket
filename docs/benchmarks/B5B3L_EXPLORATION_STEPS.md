# B5b3l — профиль шага героя и обновления исследования

Дата: 14 ноября 2026. Рабочие модули приложения точно соответствуют базе `4316e17134a7526371889eaceffbffc54ebf06c4`. Изменены только диагностические скрипты, тест и документация. Ускорение приложения этим срезом не реализовано.

## Сценарий и эталон

Новый --exploration-updates on взаимно исключён с --state-updates on; оба выключены по умолчанию. Одноразовая кампания содержит прежнего наблюдателя и второго героя, который пять раз идёт на восток (1308,8 → 1313,8), пересекая границу чанков 40,0 / 41,0 на четвёртом шаге. Приглашение выдаётся через настоящий мастерский API, шаг — через /api/player-position/move с Bearer и текущей ревизией. У каждого GET общего экрана нет мастерской cookie и Bearer. Временные токены/пароль не входят в отчёт.

Сохранены 3 000 объектов и 150 000 тайлов: 225 клеток перенесены из удалённой области в коридор. Начальная память — 149 822 клетки, 2 995 объектов. На малом профиле 8 исходных объектов заменяются 10 диагностическими, допуск приложения соблюдён. Пробы включают прежнюю позицию бочки, устаревший каменный пол, неизвестную клетку, скрытый сундук и отдельно раскрытый сундук. Полоса воды проверяет отказ движения.

scripts/world-table-movement.cjs строит ожидаемую последовательность через независимые remember/project из test/fixtures/world-exploration-linear.cjs (эталон до индекса, Git blob `beca42981ad7a6ba62b4aaeb5798eefffa2250f0`). Сервер эту копию не загружает. LOS для эталона использует действующий world-movement, поэтому это не независимая проверка самого алгоритма лучей. Отдельные явные проверки требуют открытия неизвестной клетки первым шагом, замены старой позиции бочки, сохранения нового пола после ухода из обзора, отсутствия нераскрытого сундука и наличия раскрытого.

## Метод и воспроизведение

Пять последовательных финальных прогонов: два с туманом и стадиями, один без тумана со стадиями, по одному контролю on/off без обёрток стадий. Все sourceSha256 одинаковы во всех пяти; рабочие Git blob свёрены с базой. --stages off всё ещё использует guarded IPC/I/O-probe: это контроль обёрток стадий, а не полностью свободный от диагностики сервер.

На прогон: 7 первых GET отдельно в warmupRows, затем 5 подтверждённых шагов и 35 GET в rows. Порядок: status, near, adjacent, distant, live, empty, walk. Первое чтение объектов near строит индекс памяти; walk идёт последним и читает новый регион уже после построения. После замеров 3 отклонённых команды (401 без приглашения, 409 устаревшая ревизия, 409 вода) и 7 повторных GET. validationRows не входят в summary; повторные GET побайтово равны последнему измеренному состоянию.

Итого 25 шагов, 175 измеренных GET, 35 первых GET и 50 запросов проверки отказов/сохранности. Сырые метрики команд в updateRows, отдельная сводка updateSummary. updateCycles.firstReadsMs — status + near; updateAndFirstReadsMs добавляет шаг. walkMs — отдельный последний GET, он не входит в эти суммы. Медиана суммы вычислена по циклам, а не сложением независимых медиан.

```sh
node scripts/world-table-benchmark.cjs --profile limit --samples 5 --fog on --exploration-updates on --stages on --ref 4316e17134a7526371889eaceffbffc54ebf06c4 --output /tmp/exploration-step.json
```

Повторить для --fog off и --stages off. Выходной файл должен отсутствовать. Node.js 24.22.1, Linux/loopback, тёплый OS-кеш, без принудительного GC. Временные кампании удаляются после завершения.

С включённым туманом post-save уведомление ТВ вызывает projectionRevision внутри команды: там уже загружается/разбирается/замораживается свежее состояние. Поэтому первый status не читает его повторно. Без тумана публичная версия не включает sight, уведомление не создаётся, и загрузка откладывается до status. Шесть вместо пяти readPublished без тумана обусловлены повторной попыткой explorationNotice(position) после null для старой позиции, даже в той же карте.

Живой индекс сохраняется благодаря B5b3k. Память после каждого шага получает новый источник, первый near перестраивает её индекс; остальные GET его используют. Эта сцена действительно меняет память, поэтому слепое сохранение старой ссылки было бы неверным. Публичная exploration-версия увеличивается только при fog on; с fog off остаётся 2, при этом личная позиция подтверждённо получает новую ревизию.

Каждый манифест публикации — 392 673 байта с туманом / 392 674 без, суммарно за шаг 1 963 365 / 2 356 044 байта. Начальный positions — 4 018 012 байт, после шагов растёт; каждая запись сохраняет весь JSON. readBytes считает readFileSync, не stat/exists/rename и не все системные I/O.

Стадии не следует складывать по inclusive totalMs. Эксклюзивный selfMs включает собственный код метода, не только JSON. В двух fog-on прогонах positions.projectionRevision внутри шага стоит 19.96 / 20.11 мс self; пять store.readPublished — 8.70 / 8.30 мс self, плюс их io.publishedManifest 3.64 / 1.43 мс. Неохваченный остаток включает readState parse, сериализацию записи и прочий код; эти части отдельно не приписываются конкретной функции. io.write измеряет writeFileSync, сериализация до него и rename остаются вне этой стадии.

## Следующий безопасный срез

**B5b3m — read-only публикация в чтениях команды исследования.** Убрать повторный полный readPublished из read-only цепочки stepVisibility/capture/уведомления, используя существующий guarded readPublishedView. Данные для мутаций публикации оставить независимыми, terrain читать свежим по ключам. Проверить точное равенство команд и последовательностей GET, смену публикации/двери/секрета/кампании, отказы записи и холодный fallback; повторить этот стенд против точной базы. Тёплый шаг не должен повторно читать неизменённый манифест; измерить полную команду и первые чтения, не только одну стадию.

Это ограниченный следующий шаг по измеренным пяти/шести полным разборам существующего манифеста, без новой схемы. Он не обещает устранить основной полный positions JSON, запись/замораживание или перестроение памяти. Эти расходы, холодное чтение и дисковый индекс остаются открыты. B5b3 и огромный мир целиком не готовы. Графика, FPS, браузер, LAN, Windows и физические устройства заново не проверялись.
