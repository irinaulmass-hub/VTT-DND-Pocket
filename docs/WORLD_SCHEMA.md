# Схема мира и координаты

Контракт B1 для следующих задач хранения. Версия 1 описывает целевой формат. B3 вводит раздельное хранение чанков для новых карт на одном слое. Поля целевой многослойной модели вводятся отдельно.

## Записи версии 1

| Запись | Ключ в пределах кампании | Данные |
| --- | --- | --- |
| Мир | `worldId` | `schemaVersion: 1`, стабильный ID, имя, ревизия черновика |
| Сцена | `worldId, sceneId` | Имя и назначение сцены. В каждом мире есть `overworld`. Интерьеры и подземелья могут быть отдельными сценами |
| Этаж | `worldId, sceneId, floorId` | Стабильный ID и целочисленный `elevation` для отображения порядка. Базовый этаж имеет ID `ground` и высоту 0 |
| Чанк местности | `worldId, sceneId, floorId, cx, cy` | Разреженные клетки `offset → terrainId`. Пустой чанк можно не хранить |
| Объект | `worldId, sceneId, floorId, objectId` | Координаты опорной клетки, тип, поворот и параметры. Объект хранится один раз; поиск по области учитывает всю занимаемую им площадь |
| Позиция героя | `characterId` | `worldId, sceneId, floorId, x, y`. Высота выводится из этажа. Модель движения и проверки прав реализуются в C |
| Память героя | `characterId, worldId, sceneId, floorId, cx, cy` | Открытые клетки и последнее известное состояние местности. Текущая видимость вычисляется отдельно. Реализация в E |
| Публикация | `worldId` | Ссылка на опубликованную ревизию карты, отдельная ревизия игрового состояния и данные общего экрана. Публикация остаётся стабильной при правках черновика |

Кампания задаёт внешний контекст всех ключей. ID сохраняются при переименовании. `floorId` определяет слой, а `elevation` задаёт его порядок и не входит в ключ. Объекты и секреты хранятся на стороне сервера. Выдача клиентам проходит через отдельные проекции с проверкой прав.

## Координаты

- `x` растёт вправо, `y` вниз. Оба значения — целочисленные координаты клетки в сетке сцены. Этажи одной сцены используют одну сетку. Разные сцены могут иметь разные начала координат. Переход хранит явную точку назначения, включая сцену и этаж.
- Камера, пиксели и положение внутри клетки относятся к отрисовке. Растровые сцены используют собственную модель. Перевод их нормализованных координат в клетки требует явной привязки карты к сетке.
- Чанк имеет размер 32×32. При пересечении нуля используется округление вниз: `cx = floor(x / 32)`, `cy = floor(y / 32)`. Локальные координаты `lx = x - 32*cx` и `ly = y - 32*cy` лежат в диапазоне 0–31. Индекс строки `offset = ly*32 + lx` лежит в диапазоне 0–1023.
- Обратное преобразование: `x = cx*32 + offset % 32`, `y = cy*32 + floor(offset / 32)`. В прежнем JSON ключ чанка сериализуется как `"cx,cy"`. Канонические ключи не имеют ведущих нулей и отрицательного нуля.
- Реализация редактора сейчас принимает клетки в диапазоне от −8192 до 8191 включительно. Размер чанка не зависит от этого ограничения. Повышение лимита требует проверки API, хранилища и отрисовки.

| Клетка | Чанк | Индекс |
| --- | --- | --- |
| (0, 0) | (0, 0) | 0 |
| (31, 31) | (0, 0) | 1023 |
| (32, 32) | (1, 1) | 0 |
| (−1, −1) | (−1, −1) | 1023 |
| (−32, −32) | (−1, −1) | 0 |
| (−33, 32) | (−2, 1) | 31 |

## Версии и перенос

- Формат без `schemaVersion` считается прежним только после проверки ожидаемой структуры. `revision` — версия содержимого для контроля конфликтов, `schemaVersion` — версия структуры. Неизвестная версия должна завершать чтение явной ошибкой без перезаписи.
- При импорте каждый прежний мир сохраняет ID и остаётся на единственном слое, соответствующем будущему `overworld / ground`. Координаты, ревизии, объекты, опубликованный снимок и общий туман переносятся отдельно от черновика. Общая маска не превращается автоматически в персональную историю героев.
- Старый валидатор пропускает некоторые неканонические строковые ключи. Импорт должен обнаруживать их и сообщать о конфликте, если несколько ключей приводятся к одной клетке. Исходные файлы сохраняются. B4 проверяет конфликты, прерванную запись и повторный запуск.

## Файловое хранение B3

- Новые миры имеют два независимых манифеста в каталоге `worlds`: `<id>-chunks.json` для черновика и `<id>-live-chunks.json` для публикации. Поле `storageVersion: 1` версионирует этот файловый формат отдельно от целевой схемы мира.
- Индексы сопоставляют ключу чанка SHA-256 содержимого и число тайлов. Неизменяемые файлы чанков лежат в `<id>-chunks/`. Сначала записываются новые файлы, затем манифест заменяется переименованием. Прерванная запись до замены может оставить файл без ссылки. Удаление таких файлов в B3 не выполняется.
- ТВ читает метаданные и запрошенные файлы местности. Объекты, общий туман и индекс пока хранятся в манифесте. Полное чтение, полная запись и публикация продолжают поддерживаться, в том числе для текущего интерфейса редактора.
- Мастер может запросить до 100 чанков через `GET /api/worlds/:id/chunks?chunks=0,0;1,0`. Ответ содержит ID, ревизию и запрошенные существующие чанки. `PATCH /api/worlds/:id/chunks` принимает `{ revision, chunks }`, заменяет перечисленные чанки целиком и удаляет чанки со значением `null`. Успешный ответ содержит новую ревизию. Устаревшая ревизия возвращает HTTP 409.
- Для прежних JSON выборочный GET отфильтровывает данные после полного чтения. Полная запись сохраняет прежний формат, а PATCH возвращает HTTP 409. Импорт активирует чанковый режим для выбранной карты.


## Перенос и откат B4

1. Остановите сервер и создайте отдельную резервную копию по [инструкции](TESTING.md#резервная-копия-и-восстановление).
2. Выполните `node import-world.js "<каталог данных кампании>" <id-мира>`. Для кампании по умолчанию укажите корень `DATA_DIR`, для отдельной кампании — `DATA_DIR/campaigns/<id-кампании>`. Запускайте один процесс импорта за раз.
3. Запустите сервер и проверьте карту в редакторе и опубликованный снимок на телевизоре. Повторный запуск команды для импортированной карты возвращает `already imported` и сохраняет последующие правки.

Импорт проверяет черновик и публикацию до записи, нормализует индексы местности и тумана и сообщает об ошибке, если две записи указывают на одну клетку. Исходные `<id>.json`, `<id>-live.json` и указатель активного мира остаются на месте. Манифест публикации записывается первым. Переключение на чанки происходит только после появления манифеста черновика. Если запись прервалась раньше, после устранения причины можно повторить импорт.

Для отката восстановите резервную копию в отдельной установке и проверьте её по инструкции. Исходные JSON отражают состояние до импорта. Правки, сделанные после перехода на чанки, находятся в импортированной установке.


## Сохранение личной позиции C2

В файле character-positions.json каждой кампании раздел positions хранит одну текущую запись на ID героя. Запись содержит characterId, worldId, sceneId, floorId, x и y. Новое назначение позиции заменяет прежнюю запись героя. Файл заменяется атомарно через временный файл. Его охватывает резервная копия каталога кампании.

Мастер выбирает мир и героя в редакторе, включает инструмент «Поставить или перенести героя» и нажимает клетку. GET и PUT /api/character-positions/:characterId позволяют мастеру читать и задавать эту позицию. Приглашённый игрок читает свою запись через GET /api/player-position с действующим Bearer-приглашением. До первого назначения поле position равно null. Поиск мира выполняется в текущей кампании. Корневая карта имеет сцену overworld. Вложенные карты задают дополнительные сцены на этаже ground.

Позиция хранится отдельно от общей проекции телевизора. Публичные жетоны и открытые участки меняются через действующие команды общего экрана. Текущий обзор каждого героя участвует в общей проекции телевизора. Личная карта телефона относится к G3.


## Шаги и перенос C3

Запись содержит revision. У записей C2 без этого поля версия считается равной нулю. Установка мастером и каждый успешный шаг повышают версию на единицу. Перенос мастером использует PUT /api/character-positions/:characterId и допускает другую карту текущей кампании.

POST /api/player-position/move принимает direction (north, south, west или east) и revision. Сервер определяет героя по Bearer-приглашению и вычисляет координаты соседней клетки. Запрос со старой версией получает HTTP 409 и текущую позицию. Действующая блокировка движения возвращает HTTP 403. Изменение публикуется через личное событие CHARACTER_POSITION для мастера и назначенного игрока, включая первоначальный вход по приглашению. Шаги проверяют границы координат и проходимость. В C4 добавлена команда enter для перехода между сценами.


## Общая карта путешествия группы

Позиции героев остаются отдельными. Для каждой комбинации мира, сцены и этажа раздел explored хранит общую маску подтверждённых шагов. Успешный шаг добавляет клетку отправления и видимые клетки вокруг точки прибытия. Маска и позиция сохраняются атомарно в character-positions.json. Существующие файлы позиций читаются без предварительного переноса и получают маску при первой записи.

При включённом тумане телевизор получает объединение этой маски и ручных открытий мастера для опубликованной карты. Скрытые объекты и личные координаты через этот механизм не передаются. Перенос мастером сам по себе ничего не открывает. Открытия, сделанные до публикации карты, появятся при её показе.


## Проходимость и переходы C4

В редакторе можно создать карту как сцену существующего мира. У карты есть parentWorldId и стабильный ID, который используется как sceneId. Корневая карта сохраняет sceneId overworld. Сцены используют этаж ground. Публикация отдельной сцены на телевизор показывает её маску исследования.

Мастер открывает «Переходы между сценами», выбирает исходную клетку, карту назначения и координаты. Сервер проверяет принадлежность обеих сцен одному миру и проходимость обеих клеток. Связь односторонняя. Для возврата мастер создаёт обратную связь. Сохранение новой связи из той же клетки заменяет прежнюю. Мастерские GET и POST /api/worlds/:id/transitions читают и записывают связи. DELETE /api/worlds/:id/transitions/:linkId удаляет связь. Файл world-transitions.json входит в каталог кампании.

Игрок нажимает «Войти в переход» во вкладке «Путь» на исходной клетке. Сервер находит связь по сохранённой позиции, повторно проверяет клетку назначения и открывает клетку отправления и видимую область в сцене назначения. Телевизор переключает сцены по команде мастера.

Стены, ограды, частоколы, двери, здания, колодцы, деревья, валуны и повозки блокируют движение. Вода проходима под мостом. Пустая клетка доступна. Сервер проверяет геометрию опубликованной версии карты, если она есть, иначе читает черновик. Для нового шага загружается чанк клетки назначения и список объектов. Закрытые двери блокируют шаг. Открытые двери и дополнительные этажи описаны в E2.


## Обзор после шага E1

Общая маска дополняется после успешного шага или перехода. Из точки прибытия сервер проверяет прямую видимость каждой клетки в радиусе четырёх клеток, включая соседние чанки. Стены, ограды, частоколы, двери и твёрдые объекты прерывают обзор. Клетка первого препятствия видна. Просвет по диагонали между двумя непрозрачными клетками закрыт. Вода перекрывает движение, но остаётся видимой. Перенос мастером, отклонённый шаг и повтор запроса с устаревшей версией не добавляют клетки в маску.

Для расчёта используются объекты опубликованной карты, если она существует, иначе объекты черновика. При открытии клеток телевизор запрашивает обновление активной сцены. Маски сцен разделены, а скрытые объекты фильтруются при выдаче.


## Двери и этажи E2

На опубликованной карте мастер выбирает дверь по координатам и меняет её состояние. PUT /api/worlds/live/doors/:doorId принимает ID активной карты и значение open. По умолчанию двери закрыты. Состояние хранится по ID карты и двери в character-positions.json. Открытая дверь пропускает движение и обзор. При открытии сервер обновляет исследование для героев на этом же этаже, у которых дверь была в поле зрения. Состояние двери и открытые клетки сохраняются одной записью. При закрытии ранее увиденные клетки остаются исследованными. Телевизор показывает состояние только выданных ему дверей.

Дополнительный этаж создаётся в редакторе как карта сцены с целым номером, отличным от нуля. POST /api/worlds принимает sceneMapId и elevation. Этаж получает собственный ID карты, который используется как floorId, и сохраняет ID мира и сцены. Нулевой этаж остаётся ground. Маски, объекты, двери и переходы принадлежат своей карте. Мастер связывает этажи переходами и выбирает, какой этаж показать на телевизоре.


### Последнее увиденное состояние E3

В `character-positions.json` появились необязательные поля `observing` и `memory`. Первое связывает героя с ревизией его позиции, с которой начался обзор. Подтверждённый шаг или открытие видимой двери включает обзор. Перенос мастером сохраняет старое наблюдение и сбрасывает текущий обзор до следующего действия. Второе поле хранит память группы по ключу `[worldId, sceneId, floorId]`. В каждом слое память содержит тайлы по чанкам, значение `null` для виденной пустой клетки и последние известные публичные объекты. Состояние дверей входит в снимок видимых дверей.

Ответ `GET /api/worlds/table` при включённом тумане возвращает `seen` для всех известных клеток и `visible` для клеток, которые сейчас видит хотя бы один герой. Обе маски ограничены запрошенными чанками. Клетки в `visible` берутся из текущей публикации. Остальные известные клетки показывают сохранённое состояние. Правки за пределами обзора становятся видны при новом наблюдении или ручном раскрытии. Ручное раскрытие обновляет память, оставляя `visible` зависимой от обзора героев.

Прежние маски остаются пригодными для чтения. Перед заменой публикации сервер сохраняет снимки известных клеток, для которых раньше была только маска, из предыдущей публикации. Черновики служат для расчёта движения на ещё не опубликованной карте. Память телевизора заполняется из опубликованных карт. Формат позиции, исходные маски и опубликованные карты сохраняют совместимость.


### Раскрытие скрытых объектов E4

Опубликованный объект с `hidden: true` можно раскрыть отдельно через управление большой картой. Мастерский `PUT /api/worlds/live/secrets/:objectId` принимает ID активной карты и ревизию её опубликованного черновика. Сервер проверяет карту, ревизию и скрытый объект. Повторное раскрытие той же версии объекта идемпотентно.

В `character-positions.json` необязательное поле `revealedSecrets` хранит разрешения по ID карты и объекта. Разрешение включает тип, координаты и поворот. Состояние раскрытия и снимок одной клетки записываются вместе. Другие скрытые объекты в этой клетке требуют собственных разрешений. Видимость клетки и состояние двери рассчитываются по действующим правилам. Скрытые стены и двери продолжают участвовать в проходимости и обзоре.

После перемещения или изменения раскрытого объекта прежний снимок может оставаться в памяти за пределами обзора. Новое положение и вид скрытого объекта мастер раскрывает отдельно. Черновик сохраняет признак `hidden`. Прежние сохранения без поля `revealedSecrets` читаются как карты без явных раскрытий.


### Версия общей карты D3

`WORLD_UPDATE`, `GET /api/worlds/table` и `GET /api/worlds/table/status` возвращают поле `version` с компонентами `generation`, `publication` и `exploration`. ТВ сравнивает их в указанном порядке. Версия черновика и версия личной позиции используются отдельно для проверки конфликтов при записи.

- `generation` хранится в `active-world.json` и растёт при переключении карты или прекращении показа. Прежние указатели без этого поля читаются с нулевой версией.
- `publication` использует текущую ревизию опубликованного снимка. Она растёт при публикации, изменении кадра, перемещении публичного жетона и ручном раскрытии местности.
- `exploration` берётся из `character-positions.json`. Шаги героев, ручное раскрытие местности и изменения обзора влияют на версию при включённом тумане. Двери и явные раскрытия секретов учитываются в обоих режимах. Неуспешный шаг и повтор команды открытия той же двери или секрета сохраняют версию.

Маршрут `/api/worlds/table/status` отдаёт метаданные общей карты и состояние затемнения экрана без чтения файлов чанков. При снятии карты с показа статус содержит `id: null` и версию переключения. Публичный маршрут чанков в этом случае возвращает `null`.


### Личные открытия D4

Файл кампании `world-discoveries.json` хранит отдельный журнал для каждого ID героя. Запись содержит ID и название карты, ID объекта, тип, координаты и поворот на момент передачи. При одинаковой записи повтор безопасен. Повторная передача изменённого объекта обновляет запись по паре ID карты и объекта. Публикация правок сама по себе не меняет журнал. Отсутствующий файл означает пустой журнал.


### Рецепты генераторов F1

Поле `generators` в черновике содержит до 128 рецептов. ID уникален в пределах черновика. Для карт без этого поля список считается пустым. Первая версия описывает Path для дорог и рек.

| Поле | Формат версии 1 |
| --- | --- |
| `id` | Стабильная строка длиной до 64 символов из латинских букв, цифр, дефиса и подчёркивания. Первый символ — буква или цифра |
| `kind` | `path` |
| `version` | Целое число `1`, фиксирующее контракт параметров и поток случайных чисел |
| `seed` | Целое число от `0` до `4294967295` |
| `params.terrain` | `path` для дороги или `water` для реки |
| `params.width` | Нечётная ширина от 1 до 15 клеток. Это позволяет центрировать полосу на опорной линии |
| `params.points` | От 2 до 256 упорядоченных точек вида `{ "x": -33, "y": 0 }` в координатах клеток текущей карты. Соседние точки различаются |

```json
{
  "id": "road-west",
  "kind": "path",
  "version": 1,
  "seed": 0,
  "params": {
    "terrain": "path",
    "width": 3,
    "points": [{ "x": -33, "y": 0 }, { "x": 32, "y": 1 }]
  }
}
```

`createRandomV1(seed)` в `remote/world-generators.js` возвращает воспроизводимый поток чисел в диапазоне от 0 включительно до 1 исключительно. Каждый запуск создаёт отдельный поток. Тесты закрепляют эталонные значения, включая нулевой и максимальный seed.

Мастер читает рецепты вместе с черновиком через `GET /api/worlds/:id`. При полном сохранении через `PUT` поле `generators` заменяет список, а отсутствие поля сохраняет прежние рецепты. `[]` задаёт пустой список. Неизвестная версия, незнакомое поле или недопустимые параметры возвращают HTTP 400. Сохранение списка проверяет ревизию черновика. Инструмент Path применяет сгенерированные тайлы к черновику отдельной командой. Частичное обновление чанков сохраняет рецепты. Опубликованные снимки содержат тайлы и объекты без рецептов.


### Применение Path F2

Генератор строит непрерывную линию через все опорные клетки. На длинных отрезках seed задаёт небольшие изгибы между точками. Покрытие расширяется круглой кистью указанной ширины и обрезается у границы мира. За один запуск можно получить до 16 384 клеток. Для слишком длинной трассы редактор предлагает разбить её на участки.

Предпросмотр использует временное покрытие. При применении тайлы заменяются в пределах показанной линии. История редактора сохраняет прежние тайлы и список рецептов для отмены и повтора. Загрузка сохранённого рецепта переносит камеру к первой точке. Начиная с F4 правка точек или параметров обновляет выбранный рецепт с прежним ID; «Новый участок» начинает отдельный рецепт. Сохранение отправляет результат и рецепты в том же запросе с ревизией черновика. Правила регенерации и сохранения ручных правок описаны ниже.


### Forest Plot F3

Рецепт леса имеет `kind: "forest"`, `version: 1` и общие поля `id` и `seed`. `params.density` задаёт плотность целым числом от 10 до 100. `params.points` содержит от 3 до 64 уникальных вершин по периметру. Контур замыкается автоматически и допускает вогнутые участки. Пересечение сторон отклоняется. Ограничивающий прямоугольник может содержать до 4096 клеток.

Алгоритм учитывает исходный черновик. Он заменяет свободный грунт, траву и лесные тайлы на `woodland`, сохраняет воду, дороги, другие покрытия и клетки существующих объектов. Одинаковый рецепт на одинаковом черновике даёт одинаковое размещение. Рощи состоят из обычных объектов `tree` и `bush`. Предпросмотр временно показывает результат, а применение добавляет тайлы, объекты и рецепт в одну операцию истории. Повторное применение сохранённого леса сохраняет уже размещённые растения. Начиная с F4 смена параметров обновляет выбранный рецепт при применении.


### Регенерация и ручные правки F4

У рецепта версии 1 появилось необязательное поле `state`. Старые рецепты без него валидны. Новые применённые рецепты содержат:

| Поле `state` | Содержание |
| --- | --- |
| `version` | `1`, версия снимка, отдельная от версии алгоритма |
| `tiles` | `{x, y, before, after}` для каждой управляемой клетки. `before` — исходное покрытие или `null`, `after` — последнее сгенерированное покрытие. До 16 384 клеток Path и 4096 клеток Forest Plot |
| `objects` | Снимки автоматических растений `{id, kind, x, y, turn, hidden}`. До 3000; у Path список пуст |
| `protectedTiles` | Уникальные координаты `{x, y}` ручных исключений, до 150 000 |
| `protectedObjects` | Уникальные ID удалённых или изменённых вручную растений, до 3000 |

Сервер проверяет поля, версии, координаты, типы покрытий и растений, уникальность записей и пределы размера. Тайлы, объекты и весь список рецептов отправляются в одном существующем `PUT` с ревизией. Частичная запись чанков сохраняет `state`. Публикация удаляет весь список `generators`, поэтому исходные покрытия и исключения игрокам не выдаются.

`generationChange` создаёт чистый план изменения и временные чанки. Он возвращает исходные тайлы старого участка, убирает только неизменённые автоматические растения и заново запускает алгоритм. Результат ограничен лимитами карты. Клетки и ручные исключения другого рецепта защищены, включая пересечения с совпадающим покрытием. Автоматического наложения или объединения таких участков в F4 нет.

Редактор добавляет ручные исключения в ту же запись истории, что и покраску, стирание или изменение объекта. Поэтому даже возврат клетки к прежнему автоматическому значению сохраняет её как ручную. Перенесённые, повёрнутые, скрытые и удалённые растения не заменяются и не появляются заново. Для правок через другой редактор или API дополнительно сравнивается текущее состояние со снимком. Совпадающую по значению внешнюю правку без метаданных отличить от отсутствия правки невозможно.

«Изменить точки» очищает опорные точки, сохраняя выбранный рецепт. «Новый участок» очищает выбор и начинает независимый рецепт. Параметры и точки окончательно меняются только при применении. Отмена и повтор включают тайлы, объекты, рецепт, исходное покрытие и ручные исключения. История ограничена 50 операциями текущего открытия; после повторного открытия доступна регенерация, но прежний стек Undo/Redo не восстанавливается.

У старых рецептов F1–F3 нет достоверного исходного покрытия. Повтор такого рецепта оставляет карту как есть; изменение параметров отклоняется с предложением создать новый участок. Автоматическая миграция с догадками о прежних тайлах не выполняется.


### Именованные шаблоны F5a

Файл кампании `world-generator-templates.json` хранится рядом с другими JSON в DATA_DIR (для отдельной кампании — в `campaigns/<id>`). Отсутствующий файл означает `{ "revision": 0, "templates": [] }`.

```json
{
  "revision": 1,
  "templates": [{
    "id": "road-settings",
    "name": "Дорога между деревнями",
    "kind": "path",
    "version": 1,
    "seed": 43,
    "settings": { "terrain": "path", "width": 3 }
  }]
}
```

Для `forest` настройки имеют ровно одно поле `density`; диапазоны настроек, версия и seed совпадают с контрактом рецепта. Название после удаления крайних пробелов содержит 1–80 символов. В кампании допускается до 128 шаблонов; имена без учёта регистра уникальны в пределах типа.

Мастерский GET `/api/world-generator-templates?game=<id>` читает весь список. POST принимает `revision`, `name`, `kind`, `version`, `seed`, `settings`; UUID назначает сервер. Ответ 201 содержит обновлённый список с увеличенной ревизией. Устаревшая ревизия или занятое название дают 409, неверный формат или переполнение — 400. Запрос ограничен 8 KiB. Чтение и запись возвращают `Cache-Control: no-store`.

Поля `points`, `params`, `state` и ручные исключения не входят в шаблон. Загрузка настроек очищает точки и ID редактируемого рецепта. Только применение нового контура создаёт независимый рецепт F4 с собственным снимком. Шаблоны добавляются отдельно от черновика; существующие карты не мигрируют. Запись через временный файл и rename сохраняет прежний список при ошибке записи; повреждённый файл отклоняется без попытки перезаписать его.


### Room F5b

Рецепт `kind: "room"`, `version: 1` использует прежний контейнер `generators` черновика:

```json
{
  "id": "room-one",
  "kind": "room",
  "version": 1,
  "seed": 7,
  "params": {
    "floor": "wood",
    "points": [{"x":0,"y":0},{"x":6,"y":0},{"x":6,"y":6},{"x":0,"y":6}],
    "entrance": {"x":3,"y":0}
  }
}
```

`floor` допускает `wood`, `stone`, `caveFloor`. Вершины — координаты клеток, лежащих на периметре; замыкание автоматическое. Контур простой, стороны идут горизонтально или вертикально, 4–64 вершины, габариты до 4096 клеток. Включаются клетки на границе и внутри. После отделения периметра внутренняя область должна быть непустой и связной по четырём соседям. Угловой вход, вход вне периметра, узкий разрыв внутренней области и выход за предел мира отклоняются.

Граница без входа покрывается существующими двухклеточными `wall`; допускается общий конец соседних секций. `door` занимает только клетку входа, её ориентация следует стороне контура. ID объектов вычисляются из ID рецепта, координат и ориентации; повтор не создаёт дубликатов. Seed сохраняется как часть контракта; в первой версии он не изменяет явно заданные пол, стены и вход. Случайная меблировка пока не генерируется.

После применения `state.version: 1` содержит прежние поля F4. Для Room `tiles[].after` — одно из трёх покрытий пола; `objects` — снимки `wall`/`door`. Старые Path/Forest и сохранения продолжают читаться. Исходное покрытие восстанавливается при регенерации, ручные исключения сохраняются вместе с историей. Если новая комната пересекает клетки чужого рецепта или стены/вход конфликтуют с существующими объектами, предпросмотр отклоняется целиком. Ручные объекты внутри комнаты сохраняются. Ручное удаление стены/двери считается намеренным исключением; повтор не восстанавливает удалённый объект с прежним ID.

Сохранение использует существующий PUT черновика с его ревизией. Публикация исключает `generators` и передаёт обычные тайлы, стены и дверь. Применяются прежние правила HTTP-доступа, движения, открытия двери и общего обзора. Нового файла или миграции нет. Room-шаблоны и ссылки на внутреннюю сцену в этот формат пока не добавлены.
