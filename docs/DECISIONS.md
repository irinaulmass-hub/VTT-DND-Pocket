# Технические решения

| ID | Статус | Решение и основание |
| --- | --- | --- |
| D001 | Принято для текущего этапа | Развивать существующий сервер Node.js и Canvas-модули. Уже имеются кампании, два типа карт, редакторы и LAN-синхронизация. Сохраняем совместимые маршруты при добавлении личных проекций. |
| D002 | Принято | Список миров читает обычные файлы черновиков с именем вида `ID.json`. Резервные копии, каталоги и опубликованные `ID-live.json` не участвуют в списке. Повреждённый настоящий черновик требует отдельного сценария восстановления. |
| D003 | Принято как требование | Персональный обзор, исследование и раскрытие секрета — разные состояния. Публикация на ТВ и обмен открытием между героями — разные действия мастера. |
| D004 | К проектированию | SQLite предусмотрена ТЗ 3.0. До выбора драйвера и миграции нужен контракт операций хранилища, оценка упаковки Windows, проверка импорта на копии и восстановление исходных JSON и ассетов. |
| D005 | Реализовано в C1/D2 | Мастер выдаёт приглашение одному герою текущей кампании. Сервер хранит хеш токена. Новая выдача и отзыв закрывают прежние назначенные соединения. |
| D006 | К проверке | Tauri 2 — кандидат из ТЗ. Решение после прототипа управления процессом Node.js, открытия второго окна и проверки упаковки на Windows. |
| D007 | Принято | ТВ объединяет обзор всех героев активного этажа. За пределами обзора сервер выдаёт последнюю виденную местность и публичные объекты. Для старых масок исходная память берётся из публикации, действовавшей до её замены. |
| D008 | Принято | Раскрытие на ТВ относится к конкретной версии скрытого объекта по типу, координатам и повороту. Снимок сохраняется в памяти группы. Изменённый скрытый объект требует нового раскрытия. Личные передачи относятся к D4. |
| D009 | Принято | Версия ТВ складывается из поколения активной карты, ревизии публикации и счётчика исследования. Каждый компонент сохраняется с данными, изменения которых он описывает. После пропуска события ТВ читает статус и запрашивает полный снимок видимого участка. |
| D010 | Принято | Личное открытие сохраняется как снимок по ID героя, карты и объекта. Права просмотра проверяются при чтении по приглашению. Общий экран получает раскрытие отдельной командой мастера. |
| D011 | Принято | Рецепты генераторов хранятся в черновике карты. Тип и версия задают контракт параметров и алгоритма. Числовой seed фиксируется при сохранении, чтобы запуск с теми же параметрами мог повторить результат. |
| D012 | Принято в F4 | Снимок исходного покрытия и ручные исключения сохраняются в рецепте. Регенерация сохраняет ID участка и защищает изменения пользователя. Старые рецепты без снимка требуют нового участка при изменении параметров. |
| D013 | Реализовано и проверено в браузере в F5a | Именованный шаблон хранит только настройки и seed генератора в отдельном файле кампании. Геометрия, исходное покрытие и ручные исключения принадлежат участку. Загрузка шаблона начинает новый рецепт. Добавление проверяет ревизию списка и сохраняет прежний файл при ошибке. |
| D014 | Реализовано в F5b | Room использует контур по линиям клеточной сетки, существующие двухклеточные wall и одну door на прямой стороне. Проверка внутренней связности и периметра исключает непроходимые узкие комнаты и перекрытый вход. Конфликт с чужим участком или объектом отклоняется целиком. Новые типы стен, произвольные диагонали и меблировка не требуются для первого среза. |
| D015 | Реализовано в F5c | Вход постройки — пара переходов в прежнем JSON-массиве. Один атомарный write/rename создаёт или удаляет оба направления. Ревизии черновиков и хеш списка защищают настройку. Снимок опубликованной постройки и проверка опубликованных карт блокируют устаревшие/неподготовленные входы. Смена карты ТВ остаётся под контролем мастера. |
| D016 | Принято, V3a | Низкая мебель (стол, скамейка, кровать) занимает полный повёрнутый footprint для движения, сохраняя обзор поверх неё. Лестница проходима и использует отдельный явно заданный переход C4. Свечение факела/жаровни ограничено клеткой и декоративно; механика света не меняет существующее исследование. Новые типы используют прежний JSON объектов без миграции. |
| D017 | Реализовано ядро F5d1 | Первый District ограничен прямоугольником, двумя связанными улицами и существующими домами. Точное число автоматических домов либо помещается с проходами, либо предпросмотр целиком отклоняется. Используются F4 и прежние HTTP-сохранения. Интерфейс добавляется после защиты связей F5c, чтобы изменение генератора не разрушало входы в интерьеры. |
| D018 | Реализовано F5d2 | Закрепление домов выводится из текущих пар F5c и не сохраняется отдельным флагом. Предпросмотр District привязан к ревизии карты и хешу переходов; PUT повторяет серверный расчёт и отклоняет изменённый результат. Это сохраняет пару без общей транзакции двух файлов, поскольку регенерация пишет только карту. Обычное ручное редактирование сохраняет прежнюю семантику. |
| D019 | Реализовано F5d3 | Применение District сразу сохраняет проверенный результат. Undo/Redo используют подписанные сервером точные снимки с текущими ревизией карты и хешем переходов; восстановление не может удалить действующую связь. Подписи привязаны к карте/кампании и процессу, история остаётся в памяти вкладки без нового хранилища. |
| D020 | Измерено в I1a; реализована B5a1 | До повышения лимитов использовать воспроизводимые изолированные HTTP-замеры с исходными выборками. На 150 000 тайлов/3 000 объектов полный ответ District достигает 10.04 MB и 449.5 мс медианы; первым сокращать этот ответ с сохранением guard/истории/связей. Не менять хранилище и не повышать пределы без сравнения на том же стенде. Loopback не является приёмкой FPS/LAN. |
| D021 | Реализовано и проверено в B5a1/B5a2 | Компактный ответ District включается явным format delta-v1; без format остаётся прежний контракт. Передавать клеточные изменения и индексные изменения списков, восстанавливая точный порядок для подписанной истории. Не менять полный PUT, HMAC и формат сохранений в этом срезе. Неизменённые части мира не передавать в preview. |
| D022 | Реализовано B5a2 | Перемещение объекта считать по экранному пути указателя и масштабу начала жеста. Выбор открывает панель свойств и способен сдвинуть canvas; этот сдвиг не должен редактировать дом или ломать его привязку. Регрессия воспроизведена тестом и повторно проверена в браузере после исправления. |
| D023 | Реализовано B5b1 | Отдельный мастерский POST district-apply принимает только guard и сам вычисляет/сохраняет район. Переиспользовать проверку ревизии/переходов, прежний writeDraft и нормализацию PUT. Возвращать delta-v1 и подписанную историю с baseRevision; не принимать полные клиентские слои и не менять формат хранилища. Редактор подключать отдельным срезом B5b2. |
| D024 | Реализовано B5b2a | После неопределённого ответа District сверять актуальный снимок и ревизию одним GET; не повторять запись автоматически. Подтверждать только точный ожидаемый результат с +1, менять историю один раз. Компактное применение подключено отдельно от компактного восстановления истории B5b2b; существующий PUT Undo/Redo пока сохранён. |
| D025 | Реализовано и проверено B5b2b | Для Undo/Redo District передавать delta-v1 отдельным мастерским POST district-history и возвращать только подтверждение ревизии. Принимать результат лишь после прежней проверки HMAC полного снимка, текущих связей и клеток переходов; общий валидатор использовать также в PUT. Ограничить дельту одним рецептом/8192 клетками, сохранить 8 MiB для совместимости метаданных. Не заводить постоянный журнал, ключ, миграцию или автоматический повтор записи. Полное дисковое чтение/подпись оптимизировать после отдельного профиля. |
| D026 | Измерено B5b3a; контракт B5b3b выбран | Профилировать синхронные границы существующих методов только в preload одноразового стенда, с исключением вложенных интервалов и контролем равенства on/off. Подготовку входа подписи (нормализация/канонизация/JSON) отделять от crypto, не объявлять диагностику ускорением. Первый ограниченный срез хранилища — запись изменённых чанков с переиспользованием индекса/ревизией/атомарным манифестом и legacy fallback; подпись полного снимка и формат не менять. Реализация B5b3b ещё предстоит. |
| D027 | Реализовано и проверено B5b3b | Для двух компактных District POST использовать внутренний commit проверенных chunkChanges, с повторной проверкой ревизии/лимита и переиспользованием индекса неизменённых чанков. Записывать новые чанки перед прежним атомарным манифестом, legacy оставить полным без миграции; PUT/HMAC/связи сохранить. Число хеширований ограничено участком, но манифест/чтение остаются полными и ускорение HTTP не заявляется. Сравнивать канонические отпечатки мира без зависимости от порядка ключей объектов, сохраняя порядок массивов. |
| D028 | Реализовано и проверено B5b3c | Переиспользовать канонические неизменённые узлы только внутри одной синхронной пары before/after, после генерации, через локальный WeakMap по ссылкам copy-on-write. Не кешировать между запросами или одиночными проверками истории. Сохранить точные прежние байты JSON/HMAC, нормализацию hidden, порядок массивов и scope/ID; совместимость проверять захватом настоящего update и независимым эталоном. |
| D029 | Реализовано и проверено B5b3d | Выбирать объект по пересечению занимаемых клеток с запрошенными чанками, но авторизовать по прежней опорной клетке независимо от запроса. Память использует старую геометрию/open двери; видимая текущая позиция подавляет старую глобально. Возвращать один публичный снимок на ID без добавления соседнего terrain. Декоративные выступы и дисковый пространственный индекс — отдельные срезы. |
| D030 | Реализовано и проверено B5b3e | Визуальные оболочки хранить в общей чистой модели отдельно от физики; один crownFrame определяет прежний кеш кроны, visualBounds используется сервером и Canvas. Отступы консервативны и проверяются командами настоящей отрисовки; прав доступа/исследования выступы не расширяют. Не менять ассеты/стиль/сохранения, не заявлять пространственный индекс или ускорение без замера. |
| D031 | Реализовано и проверено V1b | Исправлять пропорции существующего моста на уровне Canvas: узкий настил, тонкие перила и согласованная тень при прежнем footprint 4×2. Сохранить центры проходимых рядов на рисунке и не мигрировать/переставлять пользовательские карты. Проверять масштаб на отдельной сцене с обоими поворотами и сухими берегами, проход — существующей моделью движения. |
| D032 | Диагностика B5b3f проверена; контракт B5b3g выбран, ещё не реализован | Измерять настоящий публичный маршрут с насыщенной памятью и отрицательными/удалёнными/пустыми регионами, сохраняя контроль без стадий и точные ответы. Сначала ограниченно переиспользовать read-only разбор состояния исследования: основной расход — полный JSON, не отбор terrain. Один допущенный документ до 8 MiB входа, путь/идентичность файла/инвалидация и независимые мутирующие чтения; не кешировать роли/видимость. Формат/лимиты сохранить, холодное пространственное чтение не считать готовым. |
| D033 | Реализовано и проверено B5b3g | В mapState переиспользовать один глубоко замороженный документ по пути/идентичности файла с допуском 8 MiB входного JSON. Сверять метаданные до/после чтения, инвалидировать до собственных записей; мутации всегда читают независимо. Ошибки/oversize не возвращают старый кеш, visible/роли/проекция не кешируются. Улучшение относится к тёплым чтениям; status/projectionRevision — следующий отдельный срез. |
| D034 | Реализовано и проверено B5b3h | Чистый projectionRevision использует тот же проверяемый read-only документ, но вычисляет версию заново по ID/fog. Явный state и мутирующие чтения сохранить, готовый статус/notice/роли не кешировать. Измерять настоящий status тем же стендом и сравнивать с точной базой; дальнейший срез — отдельный read-only путь опубликованного манифеста, не общий изменяемый кеш. |
| D035 | Реализовано и проверено B5b3i | Для общего экрана использовать отдельный readPublishedView с одним неизменяемым манифестом по пути/идентичности и допуском 8 MiB входа. Сохранять независимый изменяемый readPublished для команд, инвалидировать до записи; terrain всегда читать по текущим ключам. Legacy/ошибки/oversize не получают старый кеш. Проекцию/ответ/права не кешировать; производный пространственный индекс — следующий отдельный срез. |
| D036 | Реализовано и проверено B5b3j | Строить ограниченный производный индекс только для неизменяемых коллекций: корзины visualBounds/опоры, исходный порядок и глобальный ID-поиск. Оставлять авторизацию/маски в проекторе, сохранять полную ветку fallback и подавление старой памяти новой видимой позицией вне запроса. Учитывать стоимость первого построения отдельно от тёплых выборок; следующий срез сохраняет неизменную коллекцию при правке состояния публикации. Формат/физику/LOS/лимиты не менять. |
| D037 | Реализовано и проверено B5b3k | Сохранять один неизменяемый кандидат опубликованных объектов через инвалидацию метаданных; reuse только после свежего guarded-чтения и строгого глубокого сравнения значений/порядка. Ошибки/legacy/oversize/смена пути вытесняют, глубокий отказ сравнения даёт свежий массив. Метаданные и мутации независимы; не кешировать доступ/проекции и не менять схему. Контролируемые frame POST измерять отдельно от GET и сравнивать полные последовательности ответов; дальнейший профиль — обновление исследования. |
| D038 | Диагностика B5b3l завершена; B5b3m запланирована | Измерять реальные шаги назначенного игрока отдельно от frame, команду/первые GET/отказы раздельно. Использовать независимый линейный projector/remember и явные пробы памяти/секретов; stages off — контроль обёрток, не отсутствие всей диагностики. По пяти/шести полным чтениям публикации выбрать ограниченное применение существующего readPublishedView в read-only цепочке команды. Не выдавать профиль за ускорение; positions JSON/запись/замораживание и индекс памяти требуют отдельных срезов. |
